# Observability and evaluation audit

Audit of the repository as of branch `feature/voice-agent-evaluation-dashboard`
(uncommitted). Facts below come from reading the code and from verified runs; the
last section lists what is NOT verified.

## How the app represents things

| Concept | Where | Notes |
|---|---|---|
| User / assistant / tool messages | `Message.role` (`user`, `assistant`, `tool`), `api/models.py`, `api/chat.py` | Tool messages carry `tool_call_id` and a JSON outcome. |
| Conversation id | `Conversation` row (chat and voice) | Attached to traces as `session_id` metadata on a `chat_turn` / `voice_retrieval_turn` parent run (added; verified offline with the real SDK, **not yet seen in LangSmith**). |
| Voice session | Pipecat pipeline in `voice/bot.py` (Groq STT, Groq LLM, Deepgram TTS) | Only text transcripts and timing (`voice/turn_recorder.py`) exist. **No audio is stored or traced.** |
| Retrieved documents | `search_knowledge` (`api/knowledge.py`), shared by chat and `voice/rag.py` | Traced as `retrieval` with counts and headings. |
| Lead + consent | `Lead` row with `consent_prompt` / `consent_reply`; `save_lead_from_tool` enforces the gate | Traced as `tool_save_lead` (no lead details). |
| Reference answers | none; golden cases hold `required_facts` and `expected_sources` | **0 cases human-reviewed**, so "correctness" has no trusted reference yet. |

## What is traced (verified by read-back)

* Errors on a parent run record only the exception type name.
* Content redaction: counts, headings and status only unless `LANGSMITH_TRACE_CONTENT=true`.

## Dashboard

Existing page `/dashboard/evals` (static HTML + org-authenticated `/v1/evals/*`). It now
also shows the metric registry with numerators, denominators, 95% Wilson intervals,
provisional thresholds and the evaluator catalogue (`evals/registry.py`). It reads local
run artifacts only; it does not call the LangSmith API. It has run filters (mode, status, dataset, published to
LangSmith), a trend chart (gaps, never zeros), an evaluator panel (scored/passed/insufficient/errors/skipped per
evaluator with version and model), failed examples that include evaluator findings, a token card (provider-reported only;
cost always N/A) and the in-process monitoring card. Verified in headless Chromium in the container against real saved
runs plus one synthetic judged run; **not yet opened in your own browser**. No thread or voice-quality section: no such data exists.

## Constraints and gaps

* Playground: it can test a prompt and model only. It cannot invoke the Pipecat voice agent, the retrieval gate or the consent gate; a Playground result is not an agent result.
* Online evaluators and alerts are LangSmith UI/plan features. None are configured, so none are claimed active.
* Token usage: recorded on `llm_call` traces and totalled per run from provider reports; per-case tokens are not stored. Cost: no pricing configured, so never computed.
* Thread-level conversation evaluators need `session_id`/`thread_id` metadata and multi-turn data; neither exists.
* Audio, interruption, affect and WER evaluators need retained audio or reference transcripts; none exist.
* Image evaluators: no image workflow; deliberately not enabled.
* Plan limits: not checked (the SDK does not expose them); confirm retention, rule and alert quotas in the LangSmith UI.

## Where each metric lives

* **Trace-level** (one run): retrieval latency, `llm_call` tokens/latency, tool outcome, per-case feedback `eval_*`, `recall_at_K`, `precision_at_K`, `mrr`, `case_passed`.
* **Thread-level**: none. Needs `session_id` on a multi-turn dataset plus a thread evaluator; not available.
* **Dataset-level / experiment-level**: LangSmith experiment means of the feedback keys above.
* **Aggregate-level (local)**: dashboard `run.*`, `retrieval.*`, `lead.*`, `eval.*` rows. `tests/test_master_metrics.py` asserts that, for the same case scores, the mean of each LangSmith feedback key equals the dashboard metric (offline). The live comparison on a real experiment has not been made.

## 2026-10-27 judge timeout fix (offline only; no live call, no LangSmith write)

* **Evidence:** before this change `build_gemini_judge_llm` passed `settings.llm_timeout_seconds` (default 20 s, `.env.example` 20) to the Gemini client, so the judge did inherit the chat timeout. That the 20 s limit caused the `ReadTimeout` is consistent with the request being non-streamed (the whole answer must arrive before the first byte) but is **not proven**; only a rerun would show it.
* **New setting:** `GEMINI_JUDGE_TIMEOUT_SECONDS` (optional; > 0 and <= 600; invalid values fail at startup with a readable message). **Default when unset: 60 s**, applied only to Gemini judge calls. `LLM_TIMEOUT_SECONDS` and everything the voice agent uses (chat, STT, TTS, Pipecat) are unchanged; tests assert the two settings are independent. Backward-compatibility note: the judge no longer follows `LLM_TIMEOUT_SECONDS`.
* **Retries:** unchanged count (2 retries). Changed *what* is retried: a read/write timeout is **no longer retried**, because the request had already reached Google and may be running and billed, so a retry would double the cost of a slow answer. Connection failures and HTTP 429/5xx are still retried (the call produced no answer). Worst case for one judge call is now one 60 s attempt on timeout, or three quick attempts on connection errors.
* **Error codes (short, content-free):** `gemini_timeout_<N>s_1_attempt_no_retry`, `<ExceptionType>_after_<n>_attempts`, `gemini_http_<status>[_after_<n>_attempts]`. Each failed judge also logs one WARNING with the evaluator name, model label and that code only; no key, prompt or reply.
* **Separation preserved:** a timeout is an evaluator `error` (no score), counted in `judge_errors` and `evaluator_errors`, never in the score means.
* **Still unverified:** whether 60 s is enough for `gemini-3.8-flash` on your account; whether the earlier retries were billed.

## 2026-10-27 review readiness, excluded cases and partial-review status (no labels were created)

* **Excluded-case policy (decision: preserve excluded cases, never delete them).** A new dataset `review_status` value `excluded` (named reviewers required, like `reviewed`) records a deliberate reviewer decision to keep a case out of validated metrics. It is accepted only when the reviewer sheets back it (every reviewer flagged `ambiguous`/`exclude`, or a recorded resolution with `final_ambiguous_or_exclude`); otherwise it is a readiness blocker. The runner skips excluded cases ("excluded by reviewers"), so they never enter a numerator or denominator. Existing records without the field still load as `unreviewed`.
* **Readiness:** every case must be an eligible metric case (marked `reviewed` and `approved`/`resolved`) or a confirmed exclusion. A dataset with zero eligible cases is never ready. Previously a case the reviewers excluded could not be reconciled with the old rule and blocked readiness forever.
* **Partial-review status:** `review_state` is one of `not_started`, `in_progress`, `unresolved`, `awaiting_dataset_update`, `evidence_inconsistent`, `identity_unverified` (added 2026-10-28), `no_eligible_cases`, `ready`, derived from reviewer sheets plus the dataset flags, not from a flag alone. Previously the "no case is reviewed" warning vanished as soon as one case was flagged `reviewed`, and the metric registry labelled such runs `measured`. Now runs store a `dataset.review` snapshot and the CLI, `summary.md`, registry and dashboard stay provisional until the state is `ready`. Runs made before this change carry no snapshot and are shown as "did not record reviewer evidence".
* **Audit fixes:** one person in two files no longer counts as two reviewers; a sheet named `-golden`/`-candidates` is only applied to its own dataset and mismatched ids are reported; duplicate dataset ids, unknown `review_status` values, malformed JSON and a missing review directory are reported with actionable messages; `fingerprint` added; new `--text` and `--require-ready` options. The status command is read-only and deterministic (tested).
* **Known limits:** the same-person check relies on file names; a resolved (previously disputed) case is not compared with the dataset's expectations; ~~the correctness judge treats any `reviewed` case as having a reference built from the author's `required_facts`~~ (fixed in the 2026-10-27 review-preparation milestone below); the candidate dataset is not used by any default command.
